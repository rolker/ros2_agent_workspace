# Planning-document kinds and the two-root rule

**Kind**: design draft
**Status**: Draft — proposed, not binding. See [Promotion path](#promotion-path-to-an-adr).
**Date**: 2026-09-17 — revised 2026-09-18 (decisions and drafts across the deployment boundary)
**Issue**: [#628](https://github.com/rolker/ros2_agent_workspace/issues/628)

This page is a *design draft*: one of the supporting kinds it defines below, and
its own first worked example of that kind. It proposes a vocabulary rather than
ruling on one. Nothing here is an Architecture Decision Record, and nothing here
binds a project repo.

## Context

Every scope this workspace touches — the workspace itself, the marine-autonomy
framework repo, each platform repo — carries some subset of the same four
planning artifacts: a statement of *why*, a statement of *what next*, a record
of *what was decided*, and a periodic statement of *what is currently wrong*.
The subsets differ, the names differ, the locations differ, and only one of them
has a working loop: the BizzyBoat roadmap
([`unh_echoboats_project11/docs/roadmap.md`](https://github.com/rolker/unh_echoboats_project11/blob/main/docs/roadmap.md)),
which stays current because deployments force a periodic read of it. This
workspace has a `README.md` § Vision, nineteen ADRs under `docs/decisions/`, and
until this change no roadmap at all.

Two consequences follow, and both are the reason for this draft:

1. **Workspace skills cannot find what they cannot name.** `janitor-sweep` and
   `audit-project` grade repos; to grade a repo's direction they have to know
   what a direction document is and where to look for one.
2. **A document with no loop goes stale silently.** The framework repo's
   `VISION.md` has not been touched since January. Nothing detects that, because
   nothing reads it on a cadence.

This draft proposes the vocabulary (what kinds exist), the structural rule (which
scopes carry them), the discovery convention (where the skills will look), and
the mechanism by which a periodic sweep publishes what it finds.

## The vocabulary of kinds

A vocabulary, **not a directory tree**. A repo is free to hold any subset.

| Kind | Answers | Edited | Written by |
|---|---|---|---|
| **vision** | Why this exists; what "done" would look like | Rarely — a change of direction, not of plan | Humans |
| **roadmap** | What is next, what is deferred, what is deliberately not here | On its own loop — each roadmap names the forcing function that makes someone open it ([roadmap template](../../.agent/templates/roadmap.md), *How this roadmap stays useful*) | Humans, with agent help |
| **decision** | What was decided and why, with a status line that also says *how* it was made | Append-only once accepted — superseded, never rewritten. A **provisional** decision is editable in place while implementation proves it, with every amendment recorded ([across the deployment boundary](#decisions-and-drafts-across-the-deployment-boundary)) | Whoever makes the decision (ADR-0001) |
| **health** | What is currently wrong or drifting in this scope | Replaced wholesale each run | Generated by the periodic sweep |

Four **supporting kinds** are used as needed and carry no structural
expectation: **reference** (how something behaves, looked up not read through),
**contract** (an interface others depend on), **design draft** (a proposal being
worked out — this page — which **names what would prove it**, see below), and
**architecture** (how the parts fit, e.g.
[`ARCHITECTURE.md`](../../ARCHITECTURE.md)).

The distinction that matters between the core four: a vision changes when the
goal changes, a roadmap changes when the plan changes, a decision never changes
once accepted (it is superseded), and health is not authored at all — it is a
measurement.

## The two-root rule

**Two roots, and only two, may be assumed by workspace tooling:**

1. **The workspace root** — this repository.
2. **The project root** — the repo a manifest entry points at.

Each may carry the four core kinds. That is the whole of the structure this
draft would have a workspace skill assume: a skill *may* assume these two
roots — and, on this draft's proposal, only these two. The header's framing
holds; nothing here binds until it is promoted.

**Below the project root, nothing is presumed.** Sub-projects, platform repos
and component repos are discovered, never enumerated:

> **A roadmap names the roadmaps beneath it.**

A roadmap that has children states them, with links; a child roadmap states its
parent. Following those links is how a collection is walked — not by scanning a
directory tree, and not by a workspace-side list of repos that would go stale the
first time a project reorganised.

This is [ADR-0003](../decisions/0003-workspace-infrastructure-is-project-agnostic.md)
expressed as structure: the workspace stays project-agnostic, so it assumes two
roots and discovers the rest. It is also
[ADR-0017](../decisions/0017-extend-agents-md-to-project-repos.md)'s stance —
project repos carry thin, referencing files, never forks of workspace content.

The operator's standing constraint, recorded on
[#628](https://github.com/rolker/ros2_agent_workspace/issues/628#issuecomment-5716595167)
(2026-09-17), verbatim:

> "Keep in mind that project11 is the project a lot of this is being developed
> against, but this workspace is meant to be agnostic to the actual project and
> should be able to work with various different ros2 projects."

**Worked examples, not sources.** `unh_marine_autonomy` is a project root: it
states its purpose in a `VISION.md` today (to be folded into a `README.md`
§ Vision), and its roadmap would name the BizzyBoat roadmap in
`unh_echoboats_project11` beneath it — a roadmap naming the roadmap beneath it.
These are the first instances this workspace will check the rule against. They
are not where the rule comes from, and any ROS 2 project can be the project root.

## Discovery by convention: the expected-location table

The skills find planning documents by probing conventional paths. There is **no
per-repo declaration file and no schema** — the operator decided this
(2026-09-17), against the alternative recorded under
[Options considered](#options-considered-and-not-taken).

| Kind | Expected location | Status of this row |
|---|---|---|
| vision | a `## Vision` section in `README.md` at the repo root | Settled by operator decision, 2026-09-17 — the better-evidenced of the two candidates (see evidence below) |
| roadmap | `ROADMAP.md` at the repo root | Settled by operator decision, 2026-09-17 — the general open-source convention (see evidence below) |
| decision | `docs/decisions/` | Settled — MADR's own literal recommendation. The kind is singular, as in the vocabulary table above; only the directory is plural |
| health | `docs/health.md` | This workspace's own choice; no external convention exists either way |

**This is a published expectation, not a requirement.** The operator, 2026-09-17:

> "I think we should at least document what kind of documents are expected where
> so we can set expectations for a project, without dictating how a project
> should store its documents."

So the table says what the workspace skills will look for, which is what lets a
project *choose* to be found. **A project that keeps a document somewhere else is
not in violation, produces no error, and is flagged by no check** — the skills'
canonical probe is these in-repo paths and nothing else, so they simply do not
find it and behave exactly as they do today. A skill may additionally *discover*
a document kept elsewhere — an org-level project board, the repo's `homepage`
field, a README link
([#634](https://github.com/rolker/ros2_agent_workspace/issues/634)) — but those
fallbacks are discovery only: they add no requirement, no check and no finding
either way. Absence is never a finding.

**It is deliberately not called a ROS 2 convention.** Nothing in the ROS 2
documentation or in the REPs locates a vision, a roadmap, an ADR directory or a
status document, and
[ADR-0008](../decisions/0008-follow-ros2-official-conventions.md)'s Decision
scopes "ROS 2 official conventions" to naming, packaging, licensing, message
design and launch structure. The table's justification is **common open-source
documentation practice plus the paths this workspace already uses** — a
`README.md` § Vision, a root `ROADMAP.md` of the kind Kubernetes sub-projects
publish, `docs/` for prose, an ADR directory beneath it. Its force comes from
being *published* (a project can meet it to be found), not from any external
authority.

**Every row is a literal path, including health.** The reader that probes these
paths is a separate piece of work, and it is contracted to probe *exactly* this
table — so the health document's name is fixed here rather than left to the
writer to invent. The vision row is the one that is not a file of its own: the
reader looks for a `## Vision` heading inside `README.md`.

**Why the health document is not at the root beside the roadmap.** An earlier
revision described it as living "beside the roadmap", which the roadmap's move
to the repo root would have dragged to a root `HEALTH.md`. It stays at
`docs/health.md`, stated plainly as **a workspace choice with no external
convention behind it**: it is generated output that is replaced wholesale each
run, and the root is reserved for the documents a human is expected to open
first.

### Evidence, and how the two contested rows were settled

Backed by a documentation-conventions survey run 2026-09-17 over ROS 2 projects
and general open-source practice. The survey itself lives under
`.agent/scratchpad/`, which is gitignored, so the sources are cited directly:

- **No ROS 2 document prescribes a location for a vision, roadmap, ADR or status
  document.** [REP-2004](https://github.com/ros-infrastructure/rep/blob/master/rep-2004.rst)
  is the only REP that touches documentation at all, and is scoped to
  package-level feature/API docs plus a per-package *quality declaration* linked
  from the README. It never mentions roadmaps, visions or ADRs. This is the
  positive evidence for the "deliberately not a ROS 2 convention" statement
  above.
- **The one ROS 2 rule about a planning document points out of the code repo.**
  The [ROS 2 Developer Guide](https://github.com/ros2/ros2_documentation/blob/rolling/source/The-ROS2-Project/Contributing/Developer-Guide.rst)
  sends design docs for significant changes to the
  [`ros2/design`](https://github.com/ros2/design) repo, published at
  [design.ros2.org](https://design.ros2.org).
- **Most surveyed ROS 2 projects keep planning documents on a separate
  documentation site or board, not in the code repo.** ros2 core's
  [Roadmap](https://docs.ros.org/en/rolling/The-ROS2-Project/Roadmap.html) is a
  page in [`ros2/ros2_documentation`](https://github.com/ros2/ros2_documentation)
  with the live feature list on an
  [org-level GitHub Project board](https://github.com/orgs/ros2/projects/70);
  Nav2's roadmap is
  [`docs/community/roadmaps.md`](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/community/roadmaps.md)
  in the separate `docs.nav2.org` repo; MoveIt's is a
  [page on moveit.ai](https://moveit.ai/documentation/contributing/roadmap/).
  This is the strongest evidence *against* an in-repo table, and the reason the
  vision and roadmap rows were contested rather than obvious. The one living
  in-repo Markdown design document found in the
  ROS 2 set is gz-sim's
  [`doc/architecture_design.md`](https://github.com/gazebosim/gz-sim/blob/main/doc/architecture_design.md)
  — which is also the shape this page takes.
- **General open-source practice keeps a lightweight in-repo stub even when the
  real planning happens elsewhere.**
  [GitHub's community-standards checklist](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)
  has no slot for ROADMAP or VISION at all; Kubernetes sub-projects keep a root
  [`ROADMAP.md`](https://github.com/kubernetes-sigs/kustomize/blob/master/ROADMAP.md)
  anyway.
- **Nearest domain evidence**:
  [`ros-maritime/community`](https://github.com/ros-maritime/community/blob/master/README.md)
  states its mission in the first line of `README.md`, keeps its roadmap on a
  GitHub Project board, and puts governance in the README rather than a separate
  file.

Row by row:

- **vision — settled on a `## Vision` section in `README.md`.** This is the
  better-evidenced of the two candidates: none of the **external** ROS 2
  projects surveyed below has a `VISION.md`, all state their mission in the
  README, and this workspace itself already uses `README.md` § Vision. The
  `VISION.md` alternative rests on a single in-house instance — the framework
  repo `unh_marine_autonomy`, whose `VISION.md` was last committed in January
  2026 and which
  [unh_marine_autonomy#394](https://github.com/rolker/unh_marine_autonomy/issues/394)
  folds into `README.md` § Vision — which is thin support for a published
  recommendation.
- **roadmap — settled on a root `ROADMAP.md`.** Three candidates were on the
  table: `docs/roadmap.md` (the BizzyBoat instance this workspace actually
  reads), a root `ROADMAP.md` (what Kubernetes sub-projects publish; the sibling
  `rolker/agent_workspace` uses `docs/ROADMAP.md`), or an external board / docs
  site (ros2 core, Nav2, `ros-maritime/community`). The root file is the general
  open-source convention and is the one form a reader can find without being
  told where to look; an external board is not a path a probe can check at all.
- **The roadmap's *shape*, as against its location, was surveyed separately**
  on the same day, over
  [Rust Project Goals](https://goals.rust-lang.org/2025h2/goals.html),
  [Kubernetes SIG Release](https://github.com/kubernetes/sig-release/blob/master/roadmap.md),
  [containerd](https://github.com/containerd/containerd/blob/main/ROADMAP.md),
  [Argo CD](https://github.com/argoproj/argo-cd/blob/master/docs/roadmap.md),
  [Prometheus](https://prometheus.io/docs/introduction/roadmap/), the
  [GitHub public roadmap](https://github.com/github/roadmap) and the sibling
  `rolker/agent_workspace`. The finding was **tweak, not switch**: none of them
  carries a named forcing function, a paired health document or a "what's not on
  this roadmap" section, so the template keeps its spine and takes four additive
  elements — a generated `Last reviewed` stamp, optional `Owner` / `Priority`
  columns, per-theme prose and a capped *Recently completed* section. The
  [roadmap template](../../.agent/templates/roadmap.md) names those sources
  itself under *Where this shape comes from*, so an instantiated roadmap can be
  traced back to them without this page.
- **decision — settled.** [MADR](https://adr.github.io/madr/) literally
  recommends creating `docs/decisions`, and it matches what this repo already
  has. No surveyed ROS 2 upstream had a named ADR practice to contradict it.
- **health — this workspace's own choice**, with no convention behind it either
  way. The nearest ROS 2 analogue is REP-2004's per-package **quality
  declaration** linked from the README — named here as an analogue, **not** a
  precedent: that one is per package and hand-written, where this is per root and
  generated.

**Settled by decision, with the survey as evidence — not by the survey alone.**
The survey above leaves the vision and roadmap rows at a genuine split, so the
choice between the candidates is a decision rather than a finding. The operator
made it on 2026-09-17, verbatim:

> "I do favor updating our own repos to follow conventions."

So the table now names the conventional form for each row, and this workspace's
own repos are brought to it: this repository's roadmap moves to a root
`ROADMAP.md` in the same change, and the two project repos follow (the framework
repo's `VISION.md` folds into a README § Vision, and the BizzyBoat
`docs/roadmap.md` is renamed to a root `ROADMAP.md`). The survey is why these
are the candidates; the operator's preference is why these two won.

**A settled row still costs a project nothing**: the table is published so a
project *can* be found, absence is still never an error, and the reader probes
whatever the table says at the time. If a row moves, the table and the reader
move together.

## Publishing what the sweep finds

### Publish means commit, not post

The periodic sweep's durable output is a **health document committed into the
repo it grades** — `docs/health.md`, the path the table fixes — replaced each
run, via a pull request. Git history is then the run-over-run diff, and the document is
readable by anyone who can read the repo, rather than living in one agent's
scratchpad.

This follows
[ADR-0015](../decisions/0015-dispatch-handoff-context-contract.md) (the
container produces, the host publishes) and
[ADR-0019](../decisions/0019-what-contains-a-dispatched-agent.md) (what
containment actually covers — "no GitHub write auth" is a property of the
launcher's token configuration, not something the sandbox enforces, so the
publish path's identity has to be *stated* rather than assumed).

Neither ADR contemplates the case this draft introduces: **a scheduled,
unattended run has no host session and *is* the publisher** — a third actor
beside the container and the interactive host. ADR-0015's reading is unchanged
for dispatched phases; what it does not cover is who publishes when nobody is
sitting there. The next two sections are that answer.

### Commit identity

A dedicated bot identity — **`Janitor Sweep Agent`**, committing on a
`skill/janitor-*` branch — the skill-worktree branch convention that the
`research` skill already uses. That convention is gated by an allowlist, and
`janitor-sweep` is **not on it today**: `worktree_create.sh`'s `ALLOWED_SKILLS`
holds `research` and `inspiration-tracker` only (verified 2026-09-17). Adding
`janitor-sweep` to it belongs to the sweep-split sub-issue that builds the
publish path this section describes, not to this draft. Set per commit with
`git -c user.name=… -c user.email=…` per AGENTS.md § Agent Commit Identity, so `check-commit-identity.py` and `check_pr_authors.py` both pass and
the PR is unmistakably automated.

### A human still reviews before merge

"Green CI is not review" (AGENTS.md § Merging) applies unchanged. This is the
workspace's first fully unattended PR-opening path, so it is stated rather than
assumed: an unattended PR is opened automatically and merged by a human.

### The trigger

**Decided (operator, 2026-09-14): a weekly Claude Code cloud Routine.** Their
stated grounds, verbatim: *"Smallest credential surface on a public repo (no new
secret stored anywhere), exact cadence, GitHub-only reach (already the rotation
rule)."*

The alternatives weighed, so a later revision can see what the choice was made
on:

| Mechanism | Cadence | New stored secrets | Reach |
|---|---|---|---|
| GitHub Actions weekly cron | Calendar-exact, laptop-independent | **2**, both on a public repo: a Claude token and a cross-repo write credential (the built-in `GITHUB_TOKEN` is scoped to the repo running the workflow) | The GitHub-origin repos the manifests declare, on a fresh clone |
| **Claude Code cloud Routine** ← chosen | Scheduled; daily run caps by plan | **0** — runs under the operator's existing Claude auth and GitHub connection | Same repo set; cloud-hosted, so no local `layers/` tree |
| anacron on the dev laptop | Boot-dependent, not calendar-exact | **0** — every credential already lives on that host | Same repo set, **plus** the local `layers/` tree |

Two things must be confirmed before the chosen mechanism is relied on, neither of
which reopens the decision: the plan's **daily-run cap**, for the weekly slot;
and that the operator's GitHub connection **reaches every overlay repo with write
access**, since the sweep commits a health document into each repo it grades and
a Routine is GitHub-repo-scoped. If the connection does not span them, that is a
scope finding to raise — not grounds to silently narrow what gets graded.

**No mechanism reaches non-GitHub (field-mode) origins, and none would**: the
sweep excludes them by URL before its rotation is built.

## The one rule stated in every roadmap

> Before choosing the next piece of work, read the roadmap and the health
> document together, once a health document exists. The roadmap says where you
> want to go; health says what will stop you. Work that appears in both goes
> first.

That sentence is what makes the two documents a loop rather than two files. The
qualification is not a hedge: no `docs/health.md` exists anywhere yet — the sweep
that writes one is
[#635](https://github.com/rolker/ros2_agent_workspace/issues/635) — and a
missing health document is normal, never a finding, so the rule has to read
correctly in the scope that has only a roadmap.

## Decisions and drafts across the deployment boundary

*Added 2026-09-18.* The vocabulary above said nothing about **tempo**, and the
first real collection it was checked against showed that to be the gap that
hurts.

### The two tempos: deployment mode and design mode

Every robotics project this workspace serves alternates between two modes,
and the boundary between them is what this section is about. In
**deployment mode** ([ADR-0014](../decisions/0014-deployment-mode.md)) the
forcing function is a date the hardware has to work by: decisions are made
fast, under the urgency contract, to get the robot out. In **design mode**
there is no such deadline, and the work is to step back and design properly
what deployment mode built organically.

**The cadence between the modes is the project's, not the workspace's.** The
project this workspace was developed against runs on a season — a summer of
deployments, then months of design — but a project that goes to the field one
day a week crosses the same boundary fifty times a year, and the rules below
are written for the boundary, not the calendar. The seasonal case is the
instance that exposed the gap. The operator, 2026-09-18, verbatim:

> "Yesterday's experience with designing the world stores was frustrating since
> ADRs were written in the field and the existing system grew quickly,
> organically, under time pressures of field deployments. Stepping back from
> that to properly design the stores has not gone as smoothly as I would hope
> so far, and it may be due to a shift in operating mode where we are now not
> under a deployment deadline. I want to make sure that what we are designing
> for documenting the designs and their states meshes well with both field
> season tempos and off season."

The two modes want different things from the same record. Deployment mode
wants capture that is fast, costs the operator nothing, and is honest that it
is provisional. Design mode wants a queue of what deployment mode decided, and
a stopping rule so the review finishes.

### What the world-store case showed

The framework repo's store-related decisions —
[uma-ADR-0002](https://github.com/rolker/unh_marine_autonomy/blob/jazzy/docs/decisions/0002-bathymetric-data-store.md),
0006, 0007, 0010, 0011 and 0013 — were all added between 2026-06-10 and
2026-08-21, inside that project's field season (verified from their git history,
2026-09-18). Three are `Proposed`, three `Accepted`. By the operator's account
above they recorded what the deployments built under pressure, and
the ADR form then did one of two things to each: an `Accepted`
one froze it ([ADR-0001](../decisions/0001-adopt-architecture-decision-records.md):
"immutable once accepted — supersede rather than edit"), and a `Proposed` one
read as undecided, so new work did not treat it as binding.

Neither status could say the true thing: *decided under pressure, working,
owed a proper look*. So when the design-mode pass began
([unh_marine_autonomy#391](https://github.com/rolker/unh_marine_autonomy/issues/391)),
it had to relitigate everything at once, and with no deadline to end it the
draft grew an evaluation and a prior-art survey before anything was adopted.
[#620](https://github.com/rolker/ros2_agent_workspace/issues/620) filed the
same diagnosis on 2026-09-03 from a different instance (uma-ADR-0013, bounded
LOD navigation, built against by three pieces of work while still `Proposed`).

### A decision records how it was made

The fix is the one #620 proposed, taken into this vocabulary rather than
issued as its own ADR: a third status, **`Provisional`**, narrowing ADR-0001's
immutability the way
[ADR-0012](../decisions/0012-permit-cross-reference-addendums-in-adrs.md)
narrowed it for navigational edits.

1. **Definition** — adopted as the working direction. New work follows it, and
   divergence is a reviewable decision that must be argued, not a free choice.
   Editable in place, Decision text included, while implementation proves it.
2. **Amendments are recorded, not silent** — an `Amended by <issue/PR>` line
   on the ADR.
3. **A conversion condition is mandatory** — each provisional decision states
   what would make it `Accepted`. Without one, provisional becomes a way to
   never decide.
4. **Conversion restores immutability** — from then on ADR-0001 and ADR-0012
   apply unchanged.

**A decision made in deployment mode would be provisional by default**, with a
conversion condition of, at minimum, a design-mode review. That is the honest
state for a field decision, and it is exactly the state ADR-0014's own "defer
is not skip" clause asks for: deferred design is *tracked*, not dropped, and
wrap-up is where completeness is restored.

The six store ADRs above are the first candidates for being marked
`Provisional` retroactively, with #391's vertical slice as their conversion
condition. That is the framework repo's call, tracked there, not here.

### A draft names what proves it

The same discipline applies to the *design draft* kind. A draft carries no
deadline, so in design mode nothing ends it. **A draft states what would
prove it** — the vertical slice, the second instance, the renderer that
selects on it — and stops growing when that thing exists or fails.

This page already does that under
[Promotion path](#promotion-path-to-an-adr) without naming the rule. The
world-store draft's vertical slice is the same thing. Naming it is what lets a
reviewer say "this rev is past the proof point" instead of asking for one
more round.

### The deployment-mode half: wrap-up lists the decisions

`/wrap-up-deployment` already consolidates the dev log and files RCA issues
from an `## RCA / Follow-up Backlog` section. It does **not** list the
decisions the deployment made. It should: a `## Decisions made this
deployment` section in the dev log, each entry naming the decision, where it
was recorded (an ADR, a config change, a field commit), and the review it is
owed. That list is what design mode reviews from. It costs the operator
nothing during the run, because it is written at wrap-up from the log, not
in the field.

This is a change to the wrap-up skill and its dev-log template, not yet filed
(see Consequences).

### The design-mode half: health lists what is owed

The health document gains a row: **provisional decisions with no review
scheduled**, aged from the date they were made. That lands in the sweep-split
work ([#635](https://github.com/rolker/ros2_agent_workspace/issues/635)) as a
finding tier beside the existing ones, and it is what makes the read-both rule
bite in design mode: the roadmap says where to go, health says which
deployment decisions are still holding the design up.

### A review pass whose cadence the roadmap names, distinct from the sweep

Two cadences, not one. The sweep is mechanical and generated: it measures,
and it lists. Reviewing a provisional decision, or deciding that a detailed
design has exposed a problem in its parent up to the vision statement, is
human work at a human cadence, run from the health document's list.

**That cadence is set by each roadmap, not by this draft.** The vocabulary
already requires every roadmap to name the forcing function that makes
someone open it; the review pass rides that same loop. A seasonal project's
roadmap says "at the field/off-season boundary"; a weekly-deployment
project's might say "monthly", or "when the unreviewed list passes N". The
workspace supplies the queue and the pass; the project supplies the clock.

This is the home the design-collection consistency review (below, still open)
has been missing: a design-mode pass that walks the collection top-down, gives
each document a verdict of *consistent / drifted / exposes a parent issue*,
and converts or supersedes the provisional decisions on the list. It is named
here as the place that process would live; the process itself is still not
specified.

### What this does not change

- Nothing here binds a project repo. `Provisional` is offered as a status a
  project's ADR practice *can* adopt; the workspace's own ADR-0001 gains it
  when this draft is promoted, not before — and the ADR template's status
  line (`.agent/templates/adr_template.md`, today `Proposed | Accepted |
  Superseded by ADR-NNNN`) gains it in the same promotion PR, so an author
  copying the template can find it. Until then the template is deliberately
  unchanged: a status the binding record does not recognise must not be
  offered by the template.
- Deployment mode's urgency contract is unchanged. Field decisions are still
  made fast and recorded in the log; the only addition is that wrap-up names
  them.
- `Proposed` and `Accepted` keep their meanings. `Provisional` sits between
  them for the case neither fits.

## Consequences

- **Enforcement is deferred, and until then these are suggestions.** This draft
  proposes two compliance rules — "a roadmap names the roadmaps beneath it" and
  the read-both rule above — with no hook, CI check or guardrail. By
  [ADR-0005](../decisions/0005-layered-enforcement-strategy.md)'s own test ("if a
  rule isn't in CI, it's a suggestion, not a rule") they are suggestions, and as
  draft text they are proposals besides. The conventional-path reader
  ([#634](https://github.com/rolker/ros2_agent_workspace/issues/634)) makes the documents the two-root rule talks about *discoverable* — it validates
  nothing and raises no finding, and discovery is the precondition for a check
  rather than the check itself, so enforcement stays owed to a scoped
  follow-up; the trigger
  ([#636](https://github.com/rolker/ros2_agent_workspace/issues/636)) gives the read-both rule its forcing function.
- **The commit-publish path does not go live until the redaction class on
  [#626](https://github.com/rolker/ros2_agent_workspace/issues/626) is closed.**
  #626 (OPEN) carries unfixed items in exactly the class that would be published:
  absolute host paths and credentials reaching stderr that the sweep report
  transcribes. Deciding "publish means commit" must not read as authorising an
  unredacted host path into a public repo. This draft proposes the destination;
  #626 is the gate on switching it on, and it is the single place those sites are
  enumerated — deliberately not copied here, where the references would be stale
  on arrival.
- **#620 is folded into this draft, not resolved as its own ADR.** The
  `Provisional` status it asked for is specified above and rides this draft's
  promotion ([#637](https://github.com/rolker/ros2_agent_workspace/issues/637));
  the ADR-0001 status addendum it proposed is part of that promotion. #620
  stays open until then, pointing here.
- **Two mechanisms are owed and not yet filed** (2026-09-18): the wrap-up
  skill's *Decisions made this deployment* section, and the roadmap-timed
  review pass. The health row for unreviewed provisional decisions is already in
  scope on #635. Until the wrap-up change lands, the deployment-mode half of the
  deployment-boundary section is a stated intention, and a deployment wrapped up
  before it lands leaves no decision list behind.
- **A new directory.** This page creates `docs/design/`. *Design draft* is a
  supporting kind, so the expected-location table prescribes no path for it:
  `docs/design/` is a local choice this repo makes, not a claim the table makes.
- **The Consequences Map gains a row** for roadmap and health documents
  (`.agent/knowledge/principles_review_guide.md`). It has no row for adding a
  prose page under `docs/` that is neither a principle nor an ADR — this page
  triggers none. Widening it to every `docs/` kind is backlog, recorded on
  [`ROADMAP.md`](../../ROADMAP.md).

## Options considered and not taken

- **A per-repo declaration file** naming each document's path, on the
  `.agents/deployment.yaml` /
  [ADR-0014](../decisions/0014-deployment-mode.md) precedent. Declined by the
  operator (2026-09-17) in favour of documented expected locations. ADR-0017's
  own Negative for that precedent is "one more per-repo file", and a declaration
  file only helps repos that adopt it — which is the same population that would
  match a published path.
- **Splitting this into two documents** — a taxonomy half (kinds, two-root rule,
  discovery) and a mechanism half (publish, identity, trigger, review gate) — so
  that superseding the trigger later does not churn the taxonomy. Declined by the
  operator (2026-09-14); it stays one document. The seam runs between
  [the table](#discovery-by-convention-the-expected-location-table) and
  [Publishing what the sweep finds](#publishing-what-the-sweep-finds), recorded
  here so a future supersede knows where it is.

## Open questions

- **The design-collection consistency review** — a process that walks a
  collection top-down and can carry a finding *up* to a parent, including the
  vision — is under discussion on
  [#628](https://github.com/rolker/ros2_agent_workspace/issues/628) and is
  deliberately not specified here. As of 2026-09-18 it has a proposed *home*
  (the [roadmap-timed review pass](#a-review-pass-whose-cadence-the-roadmap-names-distinct-from-the-sweep))
  but still no specified process.
- **What happens when the provisional queue outruns the review.** A project
  that deploys weekly feeds the unreviewed-provisional list faster than a human
  cadence drains it, and a health row nobody clears is noise. Whether aged
  entries escalate, or an overfull queue is itself a finding that the
  roadmap's loop is too slow, is not decided (raised 2026-09-18, no operator
  ruling yet).
- **Retroactive `Provisional` marking of the six field-written store ADRs** in
  `unh_marine_autonomy` — the framework repo's decision, to be raised on
  [unh_marine_autonomy#391](https://github.com/rolker/unh_marine_autonomy/issues/391).

## Promotion path to an ADR

This page ships as a draft on the operator's decision (2026-09-17), on stated
grounds of ADR fatigue from decisions issued while a design was still evolving.
What is deferred is the *binding status*, not the capture.

Promotion to a numbered ADR under `docs/decisions/` is tracked as its own
sub-issue ([#637](https://github.com/rolker/ros2_agent_workspace/issues/637)), gated on three things:

1. The conventional-path reader has landed, so the rule is exercised by code.
2. The sweep actually writes a health document, so the publish path is exercised.
3. **At least one ROS 2 project other than `unh_marine_autonomy` has exercised
   the two-root rule** — the rule is *claimed* to be project-agnostic, and one
   project cannot demonstrate that.

Promotion also **carries the pointer updates**: moving this page to a numbered
ADR changes its path, so every tracked file that links to it by path — the
roadmap, the roadmap template, the principles review guide, the instruction
files and the `inspiration-tracker` skill — moves with it in the same PR.
Enumerate them at the time with
`git grep -l 'docs/design/planning_document_vocabulary.md'` rather than
trusting this list, which ages.

The promotion also carries a cross-reference addendum on ADR-0015 under
[ADR-0012](../decisions/0012-permit-cross-reference-addendums-in-adrs.md) —
which permits an ADR pointing at another **ADR**, not at a draft, which is why
that addendum waits.
