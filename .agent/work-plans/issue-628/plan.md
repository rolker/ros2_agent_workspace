## Approach (sub-issue (1))

1. **Write `docs/design/planning_document_vocabulary.md`** — a **design draft** (`Status: Draft`), **not an ADR**. This is the operator's decision at the round-4 plan-review checkpoint (2026-09-17, comment on #628), on stated grounds of ADR fatigue; the sentence is quoted in Open Questions. The vocabulary's own **design draft** kind is therefore what ships first, and the page is its own first worked example of that kind. Sub-issue **(7)** is the commitment to promote it to an ADR once the rule has been exercised.

   **Location.** `docs/` today holds exactly `PRINCIPLES.md` and `decisions/` (verified 2026-09-17); there is no `docs/design/`, and this PR creates it. The kind → expected-location table below fixes paths for the four **core** kinds only — *design draft* is a supporting kind and the table prescribes no path for it — so `docs/design/` is a choice this PR makes locally, not a claim the table makes. `docs/` rather than `doc/` because that is what this repo already uses.

   **Structure — not the blank ADR template.** That template's Status / Context / Decision / Consequences shape is for a decision already accepted; using it would produce an ADR in everything but the directory, which is the opposite of what was asked for. The draft instead carries: a header naming its kind and `Status: Draft`; Context; the vocabulary; the two-root rule; the expected-location table with its evidence; the mechanism half (publish, identity, trigger, review gate); Open questions; References. Everything that would have been an ADR's *Decision* is written as **what this draft proposes**, and the page names (7) as its promotion path and the conditions for it.

   Covering, in one document:
   - **The vocabulary of kinds** — *vision* (why; rarely edited), *roadmap* (what next / what is deferred; carries its own loop), *decision* (ADRs, with a status line), *health* (generated by the sweep, replaced each run; `docs/health.md`, beside the roadmap), plus supporting kinds used as needed (reference, contract, design draft, architecture). A vocabulary, **not a directory tree**.
   - **The two-root rule** — **the workspace root** (this repo) and **the project root** (any repo a manifest entry points at) each carry the first four kinds, and that is the *only* structure workspace skills may assume. Both roots are named **abstractly in the draft**: the project root is "the repo the manifest points at", not any particular repo. Below the project root nothing is presumed: **a roadmap names the roadmaps beneath it**. This is the operator's standing "sub-project tier stays LOOSE" constraint, stated as a rule (ADR-0003: workspace infrastructure stays project-agnostic; ADR-0017: project repos carry thin, referencing files, never forks). `unh_marine_autonomy` and `unh_echoboats_project11` appear in the draft **only as worked examples** of a project root and a roadmap-beneath-a-roadmap — they are the first instances this workspace will check against the rule, never its source.
   - **Discovery by convention, not by declaration — and the convention is published as a table.** The draft states the two-root rule and "a roadmap names the roadmaps beneath it", and carries an explicit **kind → expected location** table:

     | Kind | Expected location | Status of this row (rev 6) |
     |---|---|---|
     | vision | a `## Vision` section in `README.md` at the repo root | Settled by operator decision, 2026-09-17 — see the evidence bullet below |
     | roadmap | `ROADMAP.md` at the repo root | Settled by operator decision, 2026-09-17 — see the evidence bullet below |
     | decision | `docs/decisions/` | Settled — MADR's own literal recommendation. The kind is singular, as in the vocabulary bullet above; only the directory is plural |
     | health | `docs/health.md` | This workspace's own choice; no external convention exists either way |

     **Every row is a literal path, including health.** An earlier revision left the health row as "beside the roadmap (`docs/`), named by the sweep" — no filename — while sub-issue (2) is contracted to probe *exactly the paths in this table*, so (2) would have had to invent the name and the single-source design would have drifted at its first reader. The name is therefore settled here, in (1), as **`docs/health.md`**: (2) probes that path, and (3) writes the document at it. (3) does not get to choose a different name without amending this table.

     The table is stated as **common open-source documentation practice, plus the paths this workspace already uses** — a `README.md` § Vision, a root `ROADMAP.md`, `docs/` for prose, an ADR directory under it — and must be justified on exactly that basis in the draft, **never derived from where any particular project happens to keep its files**. **It is deliberately *not* called a ROS 2 convention**: nothing in the ROS 2 documentation or the REPs locates a vision, a roadmap or an ADR directory, and ADR-0008's Decision scopes "ROS 2 official conventions" to naming, packaging, licensing, message design and launch structure (verified 2026-09-17 against `docs/decisions/0008-follow-ros2-official-conventions.md`). Requiring a ROS-2-convention justification would invite a fabricated citation in a document the workspace publishes as an expectation; the open-source-practice justification is honest and equally sufficient, since the table's force comes from being *published* (a project can meet it to be found), not from any external authority. The operator, verbatim, recorded as a comment on #628 dated 2026-09-17 ("Operator note recorded late", [issuecomment-5716595167](https://github.com/rolker/ros2_agent_workspace/issues/628#issuecomment-5716595167)): *"Keep in mind that project11 is the project a lot of this is being developed against, but this workspace is meant to be agnostic to the actual project and should be able to work with various different ros2 projects."* That comment is the source the draft cites for the quote — it was said during the rev-3 pass and posted after the round-3 review flagged it as unsourced; the substance restates [ADR-0003](../../../docs/decisions/0003-workspace-infrastructure-is-project-agnostic.md), which is the draft's standing authority for the same point. `unh_marine_autonomy` and `unh_echoboats_project11` are cited in the draft as **examples that happen to match**, and as the first instances to be checked against the table — not as its derivation. Any ROS 2 project can be the project root. The table is **a published expectation, not a requirement** — the operator, the same day: *"I think we should at least document what kind of documents are expected where so we can set expectations for a project, without dictating how a project should store its documents."* So it says what the workspace skills will look for, which is what lets a project choose to be found; **a project that keeps a document somewhere else is not in violation, gets no error, and is not flagged by any check** — the skills' canonical probe is these in-repo paths and nothing else, so they simply do not find it and behave exactly as they do today. A skill may additionally *discover* a document kept elsewhere — an org-level project board, the repo's `homepage` field, a README link (sub-issue (2)) — but those fallbacks are discovery only: they add no requirement, no check and no finding either way. Absence is never a finding. **No per-repo declaration file and no schema is introduced** — the operator decided this the same day, against the alternative of a small declaration file on the `.agents/deployment.yaml` / ADR-0014 precedent, which the draft records as the option considered and not taken (ADR-0017's own Negative for that precedent is "one more per-repo file"). The draft states the table and the graceful-absence requirement; **the skills that probe it are sub-issue (2)**.
   - **Evidence for the table, row by row.** It is backed by a **documentation-conventions survey run 2026-09-17** over ROS 2 projects and general open-source practice. The draft carries a **condensed evidence section**, not the survey: the survey file sits under `.agent/scratchpad/`, which is gitignored (`.gitignore:40`, verified 2026-09-17), so it cannot be cited by path and the draft cites the **source URLs** instead. What the survey establishes, and what it could not settle by itself:
     - **No ROS 2 document prescribes a location for a vision, roadmap, ADR or status document.** [REP-2004](https://github.com/ros-infrastructure/rep/blob/master/rep-2004.rst) is the only REP that touches documentation at all, and is scoped to package-level feature/API docs plus a per-package "quality declaration" linked from the README — it never mentions roadmaps, visions or ADRs. **This is the positive evidence for the "deliberately not a ROS 2 convention" statement above**, which rev 4 could only assert.
     - **The one ROS 2 rule about a planning document points *out* of the code repo**: the [ROS 2 Developer Guide](https://github.com/ros2/ros2_documentation/blob/rolling/source/The-ROS2-Project/Contributing/Developer-Guide.rst) sends design docs for significant changes to the [`ros2/design`](https://github.com/ros2/design) repo, published at [design.ros2.org](https://design.ros2.org).
     - **Most surveyed ROS 2 projects keep planning documents on a separate documentation site or board, not in the code repo.** ros2 core's [Roadmap](https://docs.ros.org/en/rolling/The-ROS2-Project/Roadmap.html) and Governance are pages in [`ros2/ros2_documentation`](https://github.com/ros2/ros2_documentation), with the live feature list on an [org-level GitHub Project board](https://github.com/orgs/ros2/projects/70); Nav2's roadmap is [`docs/community/roadmaps.md`](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/community/roadmaps.md) in the separate `docs.nav2.org` repo; MoveIt's is a [page on moveit.ai](https://moveit.ai/documentation/contributing/roadmap/). **This is the strongest single piece of evidence against an in-repo table, and it is why the vision and roadmap rows had to be decided rather than read off the survey; the operator settled both on the in-repo form on 2026-09-17.** The one living in-repo Markdown design document found in the ROS 2 set is gz-sim's [`doc/architecture_design.md`](https://github.com/gazebosim/gz-sim/blob/main/doc/architecture_design.md) — which is also the shape this draft itself takes.
     - **General open-source practice keeps a lightweight in-repo stub even when the real planning happens elsewhere.** [GitHub's community-standards checklist](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories) has **no slot for ROADMAP or VISION at all**; Kubernetes sub-projects keep a root [`ROADMAP.md`](https://github.com/kubernetes-sigs/kustomize/blob/master/ROADMAP.md) anyway.
     - **Nearest domain evidence**: [`ros-maritime/community`](https://github.com/ros-maritime/community/blob/master/README.md) states its mission in the first line of `README.md`, keeps its roadmap on a GitHub Project board, and puts governance in the README rather than a separate file.
     - **Row by row, as the draft states it**:
       - **vision — settled on a `## Vision` section in `README.md`** (operator, 2026-09-17). It is the better-evidenced of the two candidates: none of the **external** ROS 2 projects surveyed has a `VISION.md`, all state their mission in the README, and *this workspace itself* uses `README.md` § Vision. The `VISION.md` alternative rests on a single in-house instance — the framework repo `unh_marine_autonomy`, whose `VISION.md` was last committed in January 2026 and which [unh_marine_autonomy#394](https://github.com/rolker/unh_marine_autonomy/issues/394) folds into `README.md` § Vision — which is thin support for a published recommendation.
       - **roadmap — settled on a root `ROADMAP.md`** (operator, 2026-09-17). Three candidates were weighed: `docs/roadmap.md` (this workspace's BizzyBoat instance), a root `ROADMAP.md` (Kubernetes sub-projects, and what the sibling `rolker/agent_workspace` uses as `docs/ROADMAP.md`), or an **external board / docs site** (ros2 core, Nav2, `ros-maritime/community`). The root file is the general open-source convention and the one form a probe can check; an external board is not a path at all.
       - **decision — settled.** [MADR](https://adr.github.io/madr/) literally recommends creating `docs/decisions`, and it matches what this repo already has. No surveyed ROS 2 upstream had a named ADR practice to contradict it.
       - **health — this workspace's own choice**, with no convention behind it either way. The nearest ROS 2 analogue is REP-2004's per-package **quality declaration** linked from the README — named in the draft as an analogue, **not** a precedent: it is per package and hand-written, where this is per root and generated.
     - **Consequence for (7)**: the promotion gate no longer carries any row resolution — the vision and roadmap rows were settled by operator decision on 2026-09-17, and (7)'s remaining conditions are about the rule having been exercised. **Consequence for (2)**: the reader probes what the table says *today*, and if a row moves the table and the reader move together, which "(2) probes exactly the paths in this table" already guarantees. **Consequence for the table's force**: unchanged — it is published so a project *can* be found, and absence is still never an error, so a row settled against the majority external practice costs a project nothing.
   - **Publish means commit, not post** — the sweep's durable output is a health document committed beside the roadmap of the repo it grades, replaced each run via PR. Cites — but does not edit; see step 2 — **ADR-0015** (the container produces, the host publishes) and **ADR-0019** (what the container actually isolates — the "no GitHub write auth" line is a property of the launcher's token configuration, not something the sandbox enforces, so the publish path's identity has to be stated rather than assumed).
   - **Gate, stated in the draft's Consequences: the commit-publish path does not go live until the redaction class on [#626](https://github.com/rolker/ros2_agent_workspace/issues/626) is closed.** #626 (OPEN, verified 2026-09-17) carries open, unfixed items in exactly the class that would be published: absolute host paths and credentials reaching stderr that the sweep report transcribes — the resolver's two `redact.sh` refusals, the failed lock-open sites that bash reports before the `say()` funnel runs, the sweep's `mkdir -p "$REPORT_DIR"` arm, and two `redact.sh` defects that leak on hostile input (a password containing `@`; a workspace path containing `=`). **The draft cites #626 as the gate and does not restate its `file:line` references** — #626 stamps them "as of `d7b8baf`" and two of them have already moved since, so a copy in the draft would be stale on arrival. #626 is the single place those sites are enumerated. Deciding "publish means commit" must not read as authorising an unredacted host path into a *public* repo: the draft proposes the destination, #626 is the gate on switching it on, and (3)/(4) must not ship the path before it closes.
   - **Commit identity for the unattended publish path** — a dedicated bot identity (`Janitor Sweep Agent`) committing on a `skill/janitor-*` branch, the convention the `research` skill already uses, so both `check-commit-identity.py` and `check_pr_authors.py` pass and the PR is unmistakably automated. This answers the question #569's 2026-09-11 comment deferred out of that slice.
   - **An unattended PR is still reviewed by a human before merge** — "green CI is not review" (AGENTS.md § Merging) applies unchanged; stated explicitly because this is the workspace's first fully unattended PR-opening path.
   - **The trigger — decided: a weekly Claude Code cloud Routine** (operator, 2026-09-14 round-2 plan-review comment on #628). The draft records that as the mechanism the operator chose, with the three candidates and the axes they differ on (table below) as its Context, so a later revision can see what was weighed. The decision is captured here rather than deferred to (4); (4) wires what the draft records. That it is captured in a draft rather than an ADR is the round-4 decision — see the ADR-0001 row in ADR Compliance.
   - **The one rule stated in every roadmap** — before choosing the next piece of work, read the roadmap and the health document together: the roadmap says where you want to go, health says what will stop you; work appearing in both goes first.

   **Recorded option, not taken (operator, 2026-09-14): splitting the document in two** — a taxonomy ADR (kinds, two-root rule, discovery) and a mechanism ADR (publish=commit, bot identity, trigger, human-review gate), so that superseding the trigger later does not churn the taxonomy. **No mechanism reaches the gitcloud repos, and none would.** `janitor-sweep`
excludes non-GitHub origins by URL before the rotation is built
(`is_field_url`, `.claude/skills/janitor-sweep/SKILL.md` step 2 of the
repo-enumeration section), and every one of the **35** `url:` entries the rotation
actually enumerates is on `github.com` (verified 2026-09-17). 35, not 44: the
seven files under `configs/manifest/repos/` hold 44 entries in total, but
`get_overlay_repos` ignores `underlay.repos` unless `include_underlay` is set
(`.agent/scripts/lib/workspace.py:86,106`), and that file holds 9 of them. Every
entry in both sets is `github.com`, so the conclusion is unchanged — only the
count is now the one the claim is about. An
earlier revision of this table credited anacron with "full reach — the only
option that sees gitcloud repos *and* a real `layers/` tree"; the gitcloud half
of that was wrong and is corrected here.

**What `layers/` actually buys a sweep** — the whole of anacron's unique reach,
and it is narrow. The sweep and `audit-project` are built not to assume
`layers/` exists (`janitor-sweep/SKILL.md:38,197`), and
`resolve_repo_checkout.sh` falls back to a manifest-pinned clone. Two things
differ when a layer checkout is present:

1. **The two layer-dependent `audit-project` checks run instead of reporting
   SKIPPED** — the optional `colcon test` run (step 5, which needs a built
   layer workspace) and the "is it in the expected layer?" cross-reference
   (step 7). In `clone` mode both are SKIPPED, never OK
   (`audit-project/SKILL.md:152-156,254`).
2. **What is graded is the operator's working tree as it stands** — feature
   branches, uncommitted edits and all — rather than the ref the manifest pins.
   `resolve_repo_checkout.sh` documents this as a deliberate difference in
   guarantee, not a better or worse one: a `clone` was decided by the manifests,
   a `layer` checkout is accepted as is.

Whether a health document *should* grade one developer's working tree is a
design question, not just a reach one. The chosen Routine answers it by
default: health documents describe the pinned, pushed state, which is also the
state a reader of the committed document can check.

**What is *not* a discriminator.** All three run the same Claude Code agent over
the same sweep, so all three draw subscription usage and all three need
`CLAUDE_CODE_OAUTH_TOKEN` (or an API key) available to the run — the Actions row
is not "free" in the sense that matters. And **commit identity is the same
per-commit `-c` chore in all three rows**: the dedicated bot identity is set on
the commit, and `check_pr_authors.py` reads commit authors, so no mechanism is
disqualified on identity grounds. A *separate* question, which applies only to
the Routine, is the **GitHub account that opens the PR** — the operator's
connected user rather than a bot account. That is a legibility point ("is this
PR unmistakably automated?"), not a compliance one; it fails no check in this
repo. The `skill/janitor-*` branch and the `Janitor Sweep Agent` commit author
are what make the PR legible as automated under the chosen mechanism.

**The real discriminators**, with the superlatives dropped and each axis stated
plainly, are two: **cadence exactness** (Actions is calendar-exact and
laptop-independent; the Routine is scheduled but rate-capped per plan; anacron
is boot-dependent) and **new stored secrets** (Actions 2, both on a public repo;
Routine 0; anacron 0) — the third, **whether the sweep should see the local
`layers/` tree at all**, is the design question above rather than a straight
capability win. Weekly is the cadence the diff argument points to (the issue's
own "weekly is a diff, quarterly is another baseline"), and weekly is what the
operator chose.
